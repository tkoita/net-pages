1-1　前回の続きから

1-2　図1　ストリームは3段になっている

ソケットから出てくるのはバイトだけです。文字も行も、後から人間が乗せた解釈です。

ソケットから出てくるのはバイトだけ。文字も行も、上の層が後から乗せた解釈です。今日はこの3段を、下から順に自分で書きます。

★ 覚えておくこと。BufferedReader.readLine() の1行は、「バイトを集め、指定の文字コードで文字に直し、改行が来るまで待って、そこまでを1件として返す」という3段ぶんの処理です。今日は、この3段を下から自分で書きます。

1-3　図2　TCP に「境界」はない

ここが、初めてネットワークを書く人がいちばん誤解する点です。

この授業で使う取り決めは 「改行 0A までが1件」（行単位プロトコル）。第5回では、この取り決めを自分で設計します。

「行単位プロトコル」という言葉は、これだけの意味です。「区切り文字を改行にする」という、送る側と受け取る側の約束。第5回で自分たちのプロトコルを設計するとき、この約束を自分で決めることになります。

1-4　図3　文字コードは「解釈のしかた」

文字化けとは、破損ではなく読み間違いです。だからこの授業では、送る側と読む側の両方で文字コードを必ず明示します。

だから、この授業では文字コードを必ず引数で明示します。「書かなければ既定値が使われる」——その既定値が、OS・JDKのバージョン・環境変数で変わります。下の注意書きは必ず読んでください。
★ JDK 18 以降と 17 で、既定の文字コードが違います。
JDK 18 から、ファイル入出力の既定文字コードが UTF-8 に統一されました。JDK 17 の Windows 日本語環境では MS932（Shift_JIS 系）です。

つまり new InputStreamReader(in) のように文字コードを省略したコードは、隣の席と結果が変わります。今日の演習と課題では、StandardCharsets.UTF_8 のように必ず明示してください。省略したコードは、動いていても減点対象です。

1-5　★ この回で Copilot が特に間違えるところ

第1回のルール（Tab を押す前に読む／プロンプトを記録する／学籍番号やパスワードを入力しない）はそのままです。そのうえで、今日は次の3つが頻出します。

Tab を押す前に、この3点だけ見る

  • 文字コードを省略していないか。getBytes()／new String(b)／new InputStreamReader(in) はすべて引数なしで書けてしまいます。今日はすべて明示
  • newLine() を使っていないか。BufferedWriter.newLine() は Windows では \r\n（2バイト）を書きます。この授業の約束は \n（0A）1バイトです
  • flush() があるか。Copilot は write() だけ書いて終わることがあります。これが今日いちばん多い「固まる」原因です

A-2　書き足す部分

CONNECTED と表示した直後に、次の処理を足します。

やること

  • 文字列 "HELLO" を UTF-8 で byte[] に変換する
  • その後ろに 改行 0x0A を1バイト自分で足す
  • socket.getOutputStream() に write() して flush() する
  • socket.getInputStream() から 最大64バイト読む

A-3　Copilot への指示（この文面をそのまま打つ）

// 接続に成功したら、文字列 "HELLO" を UTF-8 でバイト配列に変換し、
// 末尾に改行 0x0A を1バイト足して OutputStream に write し、flush する。
// そのあと InputStream から最大64バイト読み取り、
// 読めたバイト数と、1バイトずつ "%02X " 形式の16進表示と、
// 同じバイト列を UTF-8 で文字列に戻したものを、それぞれ1行ずつ表示する。
// 文字コードは StandardCharsets を使って必ず明示すること。
★ 提案が出たら、Tab の前に2点だけ確認。
① getBytes() が引数なしになっていないか（getBytes(StandardCharsets.UTF_8) が正）
② flush() があるか

違っていたら Esc で消し、コメントを足して出し直してください。直すのではなく、出し直すのが速いです。

A-4　期待される出力

CONNECTED
SEND_BYTES=6
RECV_BYTES=6
HEX: 48 45 4C 4C 4F 0A
TEXT: HELLO

A-5　考えること

見るもの気づくこと
0A改行は1バイトの文字である。目には見えないが、確かに送られている
6バイト"HELLO" は5文字なのに、送ったのは6バイト。文字数とバイト数は違う
返りが 6バイトサーバは受け取った行をそのまま返している。だから同じ長さになる
ここまでで 0:35 です。まだ「文字」を扱っていません。扱ったのはバイトだけです。それで正しい進度です。

PART 30:35〜0:52　演習B

演習B：同じバイト列を、違う文字コードで読む

送信側は一切変えません。変えるのは「読み方」だけです。

B-1　まず、日本語を送る

演習Aの送信文字列を "HELLO" から "こんにちは" に変えて、もう一度実行してください。

SEND_BYTES=16
HEX: E3 81 93 E3 82 93 E3 81 AB E3 81 A1 E3 81 AF 0A
TEXT: こんにちは
5文字なのに 16バイトです。日本語は UTF-8 で1文字3バイト、それに改行1バイトを足して 5 × 3 + 1 = 16。この計算が合うことを、自分で確かめてください。

B-2　★ 受信側の読み方だけを変える

送信は UTF-8 のままです。最後の 「バイト列を文字列に戻す」1か所だけを Shift_JIS に変えます。

// 変える前
String text = new String(buf, 0, n, StandardCharsets.UTF_8);

// 変えた後（この1行だけ）
String text = new String(buf, 0, n, Charset.forName("Shift_JIS"));

B-3　結果を並べて比べる

読むときの指定HEX の行TEXT の行
UTF-8E3 81 93 E3 82 93 …こんにちは
Shift_JISE3 81 93 E3 82 93 …（まったく同じ）読めない文字の列になる
★HEX の行が1バイトも変わっていないことを、必ず自分の目で確認してください。

ネットワークは何も間違えていません。16バイトを送り、16バイトが返ってきました。間違えたのは、そのバイト列を「Shift_JIS だ」と思い込んだ自分のプログラムです。

文字化けを見たら、まず HEX を見る。この習慣を今日から付けてください。第9回（JSON）でも第11回（TLS）でも、同じ切り分けをします。

B-4　早く終わった人へ

  • 送信側だけを Shift_JIS にして、受信側を UTF-8 に戻すと、HEX は何バイトになりますか。（16 にはなりません）
  • なぜ英数字だけなら化けないのかを考えてください。HELLO は UTF-8 でも Shift_JIS でも 48 45 4C 4C 4F です。
  • 絵文字を1文字送ると何バイトになるか、確かめてください。（3バイトではありません）

PART 40:52〜1:08　演習C

演習C：わざと固まらせる　★ 本日の中心

ネットワークのプログラムは、間違えても例外を出しません。黙って待ち続けます。今日はそれを3回体験します。

先に止め方を確認してください。プログラムが反応しなくなったら、そのターミナルで Ctrl＋C。故障ではありません。止まって当然の状態を、これから自分で作ります。

C-1　実験①　改行を付けずに送る

演習Aで足した 0x0A の1バイトを消して、実行してください。

起きることなぜか
CONNECTED のあと、何も表示されないまま止まるサーバは readLine() で改行が来るまで待っている。だから返事をしない。こちらはその返事を待っている。両方が相手を待つ
★これがネットワークで最も多い不具合です。エラーは出ません。ログにも何も出ません。ただ返ってこないだけです。

合言葉：「固まったら、相手が何を待っているかを考える」。第3回以降、自分のサーバが返事をしなくなったとき、まずここを疑ってください。

C-2　実験②　flush() を消す

改行を元に戻し、今度は flush() の行だけをコメントアウトして実行してください。

症状は実験①（改行なし）と同じ「固まる」ですが、原因は正反対です。①は1件が完成していない。②はそもそも線の上に出ていない。

症状は実験①とまったく同じ（固まる）ですが、原因は正反対です。①は送りすぎていない（改行がない）、②はそもそも出ていない。同じ「固まる」でも、原因が複数あることを覚えて帰ってください。

C-3　実験③　\r\n で送ってみる

改行を 0x0A ではなく 0x0D 0x0A の2バイトにして送ってください。

SEND_BYTES=7      <-- 48 45 4C 4C 4F 0D 0A
RECV_BYTES=6      <-- 48 45 4C 4C 4F 0A     0D が消えている

   サーバの readLine() は 0D 0A を「1つの改行」として扱い、
   返すときは 0A だけを付けて返した。
   -> 送ったバイト列と、返ってきたバイト列が 一致しない
★ これは故障ではなく、取り決めの差です。Windows のメモ帳は \r\n、Linux と macOS は \n。BufferedWriter.newLine() は、動いている OS の流儀で書きます。

ネットワーク越しでは「動いている OS の流儀」は通用しません。だからこの授業では、改行を \n（0A）1バイトに固定します。第6回で HTTP を手で書くとき、今度は逆に \r\n が必須になります。そのとき「どちらでもいい」ではないことを、今日の実験で知っておいてください。

C-4　3つの実験のまとめ

やったこと症状原因
改行を付けない固まる相手が行の終わりを待っている
flush() を消す固まる1バイトも出ていっていない
\r\n で送る動くが一致しない改行の取り決めが違う
★3つとも、コンパイルは通り、例外も出ません。これがネットワークプログラミングの難しさです。「動かない」ではなく「黙る」。今日、その黙り方を3種類見たことが、この回のいちばんの収穫です。

演習D：ライブラリに任せる

ここまで自分で書いた処理を、BufferedReader / BufferedWriter に置き換えます。

D-1　置き換える

BufferedWriter out = new BufferedWriter(
    new OutputStreamWriter(socket.getOutputStream(), StandardCharsets.UTF_8));
BufferedReader in = new BufferedReader(
    new InputStreamReader(socket.getInputStream(), StandardCharsets.UTF_8));

out.write("こんにちは");
out.write("\n");      // newLine() は使わない。\r\n になる環境がある
out.flush();               // これは消えない。演習C-2 の通り

String line = in.readLine();
System.out.println("TEXT: " + line);

D-2　何が消えて、何が消えなかったか

自分で書いていたこといま誰がやっているか
文字列 → バイト列の変換OutputStreamWriter が、指定した文字コードで
改行までを1件として集めるBufferedReader.readLine() が
16進で確認する誰もやらない。見えなくなった
flush()自分。消えていない
文字コードの指定自分。消えていない
★ライブラリが肩代わりしたのは「手間」であって「責任」ではありません。文字コードと flush() は、最後まで自分の責任として残ります。今日の3つの実験は、すべてこの2つに関する事故でした。

そして、readLine() が返ってこないときに何が起きているかは、演習C-1 で見た通りです。

第2回 宿題 次回授業の開始まで

EchoClient.java

サーバに1行送り、返ってきたものとバイト単位で一致するかを判定するプログラムを作ります。演習Bの Bytes.java に、引数処理と出力形式を足すだけです。

実行方法

java EchoClient <ホスト名> <ポート番号> <ASCII|JP> <文字コード名>
★ 送信する文字列は、プログラムの中に持たせます。コマンドライン引数で日本語を渡させません。Windows のターミナルは、引数の文字コードが環境によって変わるためで、採点が不安定になるのを避けるためです。
  • ASCII … HELLO を送る
  • JP … こんにちは を送る（ソース中は \u3053\u3093\u306B\u3061\u306F と書いてよい）

★ 出力形式（1文字も変えないこと）

接続できた場合は 9行、順番も固定です。余計な行・装飾・空行を出してはいけません。

HOST=localhost
PORT=40001
CHARSET=UTF-8
SEND_CHARS=5
SEND_BYTES=16
SEND_HEX=E3 81 93 E3 82 93 E3 81 AB E3 81 A1 E3 81 AF 0A
RECV_BYTES=16
RECV_HEX=E3 81 93 E3 82 93 E3 81 AB E3 81 A1 E3 81 AF 0A
MATCH=true
行入れる値
HOST=第1引数をそのまま
PORT=第2引数をそのまま
CHARSET=第4引数をそのまま
SEND_CHARS=送信する文字列の文字数（改行を含めない）
SEND_BYTES=実際に送信したバイト数（改行 0A を含める）
SEND_HEX=送信バイトを %02X で、半角スペース区切り。末尾にスペースを付けない
RECV_BYTES=受信したバイト数
RECV_HEX=受信バイトを同じ形式で
MATCH=true ／ false のみ。送信バイト列と受信バイト列が完全一致すれば true

接続できなかった場合

4行だけ出して正常終了します。第1回の例外3分類をそのまま使います。

HOST=localhost
PORT=40099
CHARSET=UTF-8
ERROR=REFUSED        <-- REFUSED / UNKNOWN_HOST / TIMEOUT の3種のみ

要件

Requirements

  • 接続タイムアウトは 2000ms 固定。socket.connect(addr, 2000) を使う（第1回と同じ）
  • 例外を catch (Exception e) でまとめない。3種類に区別して ERROR= に反映する
  • 文字コードを省略しない。getBytes() ／ new String(byte[]) の引数なし版を使わない
  • 改行は 0x0A 1バイト。newLine() は使わない
  • 出力はすべて ASCII 文字のみ。送った日本語そのものは表示しない（16進で表す）
  • スタックトレースを出さない。どの入力でも、9行または4行だけ出して正常終了する
  • ポート番号が数値でない、引数が足りない等でも落ちずに終了する
  • prompt_log.md に、使ったプロンプトを3件記録する
★ 出力に日本語を含めない理由。Windows のターミナルは表示に使う文字コードが環境ごとに違うため、日本語を出力させると、正しいプログラムでも採点が落ちることがあります。「送った日本語を16進で示す」形にしてあるのは、どの環境でも同じ判定になるようにするためです。

「固まった」ときの切り分け

自分への質問「いいえ」だった場合、原因はここ
CONNECTED は出た?出ていなければ第1回の範囲です。サーバが起動していないか、ポートが違います
flush() は書いた?最頻出。1バイトも送信されていません（演習C-2）
送信バイトの末尾は 0A ?改行がないと、サーバは行の終わりを待ち続けます（演習C-1）
ターミナルを2枚開いている?サーバを起動したウィンドウは固まって見えるのが正常です。実行は別ウィンドウで
SEND_HEX を表示させてみた?推測で直さないこと。まず16進を出す。今日の演習は全部そのためにやりました

よくあるつまずき

起きること原因と直し方
何も出ずに止まるflush() がない／改行 0A がない。この2つで9割
SEND_BYTES=7 になる（ASCIIケース）newLine() を使っています。Windows では 0D 0A の2バイトが書かれます
Address already in use前に起動した EchoServer が生きています。そのウィンドウで Ctrl＋C
ターミナルに ? や 縺 が出るプログラムではなくターミナルの表示の問題。だから課題では日本語を出力させていません
lines=10 と表示されるデバッグ用の System.out.println が残っています。消してください
16進が a／e3 と小文字になる%02x ではなく %02X（大文字）を使ってください
隣の人と SEND_BYTES が違う文字コードを省略しています。JDK のバージョンで既定値が変わります（PART 1-4）

採点スクリプトの使い方

check2.ps1 は学生配布セットに入っています。次の3つを同じフォルダに置いてください：EchoClient.java（自分で書いたもの）／EchoServer.jar／check2.ps1。そのフォルダでターミナルを開き、次の1行を実行します。

powershell -ExecutionPolicy Bypass -File check2.ps1
  1. スクリプトが EchoClient.java をコンパイルする
  2. EchoServer が起動していなければ、スクリプトが自分で起動し、終わったら止める（自分で起動済みなら、それを使う）
  3. 4ケースを順に実行して、PASS / FAIL を出す
  4. 4 / 4 passed になったら提出
表示意味
PASSそのケースは仕様どおり
FAILexpected= が期待値、got= が実際の出力。両方を見比べれば、直す場所が分かります
lines=出力した行数。9（失敗ケースは 4）以外なら、出力が多すぎるか足りません
8 秒たっても終わりませんでした固まっています。flush() と改行 0A を確認してください（演習C）
警告:点数には影響しませんが、文字コードの省略や newLine() は減点対象です。直してください
★ package の行は消してください。エディタが勝手に package ...; を先頭に足すことがあります。あると java EchoClient で起動できないため、スクリプトは最初に止まります。
